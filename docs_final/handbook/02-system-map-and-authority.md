# 02. 시스템 구성과 상태 권위

## 이 구조를 택한 이유

DungeonStory는 생산, 물류, 캐릭터, 건강, 환경, 전투, 사회, 연구와 저장이 같은 세계를 공유한다. 이런 게임에서 시스템 연결이 늘어날수록 가장 위험한 문제는 기능 부족보다 상태의 주인이 불분명해지는 일이다. 창고 화면의 수량, 월드에 놓인 물건, 운반 중인 주민의 소지품과 생산 시설의 투입 대기량이 각각 별도 값을 가지면 어느 순간 물건이 복제되거나 사라진다. 사건 화면이 관계를 직접 바꾸고 세력 시스템이 다른 값을 저장하면, 같은 선택이 화면마다 다르게 보인다.

현재 구조는 각 상태에 하나의 쓰기 권위를 두고, 다른 시스템은 명령이나 질의를 통해 그 권위와 통신하도록 설계되어 있다. 이를 통해 플레이어가 본 원인과 결과가 저장 후에도 유지되고, 여러 시스템이 같은 사실을 두고 충돌하지 않는다. 상태 권위는 코드 구성 원칙이면서 게임 결과를 보존하는 규칙이다.

## 런타임의 조립 구조

한 런을 시작할 때는 중앙 조립 지점이 필수 설정과 월드 참조를 확인한 뒤 시설, 주민, 작업, 전투, 원정, 세력, 화면과 저장 체계를 연결한다.

```text
작성 자산과 카탈로그
        ↓
각 시스템의 상태와 규칙
        ↓
변경 요청과 실행 순서
        ↓
월드 객체와 읽기 정보
        ↓
화면과 표현

저장 데이터
        ↕
현재 상태와 진행 중인 행동
```

조립 지점이 한곳에 모여 있으면 어떤 시스템이 무엇을 요구하는지 확인할 수 있다. 개별 기능이 실행 도중 임의로 전역 객체를 찾거나, 등록 순서의 우연에 기대어 작동하는 경로도 줄어든다. 새 모듈은 필요한 정보와 기능을 명시하고 중앙 조립 지점이 실제 구현과 연결한다.

플레이어 입장에서는 이 구조가 보이지 않지만 결과는 느낄 수 있다. 방어 시스템이 탄약 재고를 별도로 추측하지 않고 물리 아이템 권위에 요청하므로, 생산에서 만든 탄약과 경비가 쓰는 탄약이 같은 흐름에 놓인다. 의료 시스템이 캐릭터 신체 상태를 복사하지 않으므로 원정에서 입은 부상이 귀환 뒤 병동에서도 그대로 이어진다.

## 계층별 책임

| 계층 | 소유하는 책임 | 경계를 둔 이유 |
|---|---|---|
| 콘텐츠 정의 | 안정 ID, 고정 규칙, 요구 조건, 능력과 효과 조합 | 작성 데이터와 런에서 변하는 상태를 분리한다 |
| 상태 권위 | 현재 런의 상태, 지켜야 할 규칙과 변화 순서 | 한 사실을 한곳에서만 변경한다 |
| 실행 조율 | 여러 상태를 바꾸는 순서, 사전 검사, 취소와 실패 처리 | 시스템마다 제각기 결과를 적용하지 않게 한다 |
| 월드 연결 | 씬 객체, 입력, 사건과 시각 표현의 연결 | 화면에 보이는 객체를 저장 상태의 원본으로 쓰지 않는다 |
| 읽기 정보 | 화면과 다른 시스템에 제공할 현재 상태 | 조회 과정에서 상태가 바뀌는 일을 막는다 |
| 화면 | 선택 요청, 비교 정보와 결과 표시 | 화면 코드가 저장 상태를 직접 수정하지 않는다 |
| 저장 | 버전, 의존성, 저장 내용과 복원 검증 | 불러오기 과정에서 게임 결과를 다시 추첨하지 않는다 |

이 분리는 연결을 명시적으로 유지하면서 소유권의 혼합을 막는다. 생산 결과가 세력 계약을 충족할 수 있어도 생산 체계가 세력 관계까지 직접 바꾸지는 않는다. 생산 완료 기록을 계약 체계가 확인한 뒤 물품 인계와 세력 결과를 각각의 상태에 반영한다.

## 공통 런타임 기반

여러 시스템은 다음 기반 규칙을 공유한다.

- 주요 상태 저장소
- 게임 시계와 화면 표시 시간
- 시간 배율
- 용도별 재현 가능한 난수 흐름
- 게임 이벤트 버스
- 저장 후에도 유지되는 ID 생성
- 프레임별 계산 한도와 경로 탐색 순서
- 월드 객체 목록과 복원 대상 색인
- 주민 판단이 참조하는 월드 목록

### 시간과 난수

계절, 질병, 사건, 전투와 주민의 판단에는 불확실한 결과가 있다. 모든 시스템이 같은 난수 호출 순서에 의존하면 화면 표시 한 번이나 행동 후보 수의 변화가 관계없는 전투 결과까지 바꿀 수 있다. 용도별 난수 흐름은 이런 연쇄 변화를 제한하고, 같은 입력과 상태에서 같은 결과를 재현하도록 돕는다.

게임 시계와 화면 표시 시간을 구분하는 이유도 같다. 일시정지나 시간 배율이 바뀌어도 화면 전환과 게임 규칙이 서로의 시간을 훔치지 않아야 한다. 작업 진행, 계약 기한, 질병과 계절은 게임 시간의 권위를 따르고, 화면 애니메이션은 표시 시간의 권위를 따른다.

### 실행 예산과 공정성

많은 주민이 동시에 작업을 찾고 경로를 계산하면 모든 요청을 한 프레임에 처리할 수 없다. 중앙 계산 한도는 처리량을 제한하면서도 특정 주민이나 작업이 계속 밀리지 않도록 대기 시간을 추적한다. 성능을 위해 행동 자체를 생략해서는 안 된다.

이 구조가 잘 작동하면 인구가 늘어도 주민의 판단 근거가 유지된다. 잘못 작동하면 가까운 주민만 계속 기회를 얻거나, 화면 밖 작업이 무기한 대기할 수 있다. 따라서 한 번에 처리할 판단량은 속도 제한이면서 노동 배분의 공정성 규칙이다.

## 콘텐츠 카탈로그

공용 콘텐츠 목록은 시설, 아이템, 서비스 과정, 방 환경, 전투 콘텐츠와 세션 규칙이 같은 정의를 읽도록 연결한다.

카탈로그의 역할은 자산을 편리하게 찾는 데서 끝나지 않는다.

- 어떤 콘텐츠가 현재 런에서 유효한지 명시한다.
- 안정 ID 중복과 누락을 시작 단계에서 드러낸다.
- 코드가 임시 기본 정의를 만들어 누락을 숨기는 일을 막는다.
- 저장에 남은 ID가 실제 콘텐츠와 연결되는지 검증한다.
- 여러 시스템이 같은 버전의 정의를 바라보게 한다.

콘텐츠가 등록되지 않았을 때 유사한 기본값으로 대체하면 플레이는 당장 이어질 수 있다. 그러나 비용, 해금, 저장과 화면이 서로 다른 대상을 가리킬 수 있어 원인 추적이 어려워진다. 이 프로젝트가 누락을 크게 실패시키는 방향을 택한 이유는 제작 중에 결함을 드러내고, 출시 상태에서 조용한 데이터 손상을 피하기 위해서다.

현재 콘텐츠의 안정 ID, 작성 필드, 참조와 런타임 도달 근거는 [콘텐츠 데이터베이스](../content-db/README.md)에서 유형별로 확인할 수 있다.

## 도메인별 상태 소유권

| 영역 | 한곳에서 관리하는 상태 | 보존하는 게임 의미 |
|---|---|---|
| 물리 아이템 | 월드의 물건과 인계 상태 | 물건의 위치, 수량, 예약, 현재 책임과 고유 개체 |
| 생산 | 생산 주문과 진행 상태 | 주문, 제작 중 재료, 준비된 입력과 출력, 공정 이력 |
| 연구 | 연구와 청사진 상태 | 연구 진행, 청사진, 해금과 시설 수용량 |
| 침입 | 위협, 방어 정책과 침입 진행 | 경고, 진행 단계, 교전과 시설 피해 |
| 원정 | 원정, 전투, 보상, 귀환과 도착 상태 | 출발 자산, 현재 조우, 결과와 기지 재합류 |
| 세력 | 세력별 관계와 거래 상태 | 관계, 원한, 의무, 경로와 진행 중인 거래 |
| 건강 | 신체, 의료, 수술과 인구 건강 | 부상, 질병, 면역, 치료 주문과 신체 변화 |
| 시설 진화 | 시설의 사용 이력과 진화 상태 | 실제 사용 기록, 제안, 자원과 변화 결과 |
| 사건 경보 | 현재 발생한 경보 | 경보 내용, 대응 행동과 해제 순서 |

큰 기능 하나를 언제나 한 덩어리로 저장하지는 않는다. 의료처럼 신체 상태, 치료 작업, 수술 주문과 인구 건강의 변화 규칙이 다르면 권위를 나눈다. 화면 탭이 여러 개여도 같은 상태를 다룬다면 하나의 권위를 공유한다.

실패와 저장의 원자성이 경계를 정한다. 함께 성공하거나 함께 실패해야 하는 값은 같은 변경 경계에 두고, 서로 다른 수명주기와 복구 규칙을 가진 값은 명령으로 조율한다.

## 상태 읽기와 변경 요청의 분리

화면과 다른 시스템은 저장 상태를 직접 고치지 않는다. 먼저 현재 상태를 읽고, 사용자가 선택하면 담당 시스템에 변경을 요청한다. 담당 시스템은 최신 상태에서 조건을 다시 검사한다.

화면을 연 시점과 선택을 확정한 시점 사이에는 세계가 변할 수 있다. 치료 화면을 보는 동안 다른 환자가 병상을 예약할 수 있고, 건설 명령을 준비하는 사이 재료가 생산 주문에 묶일 수 있다. 화면을 열 때 읽은 값만 믿고 변경하면 이중 예약이나 음수 재고가 생긴다.

명령의 결과는 성공과 실패만 반환하는 것으로 끝나지 않는다. 실패 원인이 플레이어가 행동할 수 있는 정보로 번역되어야 한다. 재료 부족, 수용량 부족, 경로 차단, 연구 미완료, 위험 정책 위반과 대상 소실은 서로 다른 문제다. 이 구분이 있어야 플레이어가 구조를 수정할 수 있다.

질의는 현재 값뿐 아니라 값이 만들어진 근거를 추적할 수 있어야 한다. 목표 재고에 비해 무엇이 부족한지, 어느 예약이 물건을 묶었는지, 어느 경로와 정책이 운반 후보를 제거했는지, 현재 추세가 계속되면 언제 임계점에 닿는지를 같은 원인 사슬로 설명한다. 예상값은 현재 상태와 알려진 주문을 유지한다는 가정을 함께 표시하며, 미래를 확정하지 않는다.

변경이 끝난 뒤에는 같은 항목으로 결과를 다시 읽는다. 개입 전후의 처리량, 대기량, 위험과 손실을 비교할 수 있어야 플레이어가 원인을 잘못 짚었는지 알 수 있다. 상태 조회는 운영 학습을 위한 정보다.

## 여러 시스템이 함께 참여하는 행동

여러 권위가 한 행동에 참여할 때는 보통 다음 순서를 따른다.

1. 필요한 정의와 현재 상태를 확인한다.
2. 물건, 공간, 대상과 작업 용량을 예약한다.
3. 실행 주체와 현재 책임을 고정한다.
4. 실제 작업을 진행한다.
5. 완료 영수증을 만든다.
6. 결과를 각 상태 권위에 반영한다.
7. 실패나 취소 시 예약과 남은 물건을 회수한다.

예를 들어 세력에 장비를 납품할 때는 넘길 실제 물건을 선택하고 계약 물자로 인계한다. 상대가 인수했다는 완료 기록이 생긴 뒤 세력 관계와 보상을 적용한다. 중간에 저장되더라도 같은 장비를 다시 넘기거나 보상을 두 번 받을 수 없어야 한다.

시스템은 무엇이 끝났는지, 어떤 결과가 아직 전달되지 않았는지, 이미 처리한 결과가 무엇인지 기록한다. 이 기록이 저장과 복원 뒤의 누락과 중복 지급을 막는다.

## 사건 편성에서 지켜야 할 권위 분리

사건 편성의 완성 형태에서는 호흡을 조절하는 체계와 실제 세계 상태를 바꾸는 체계를 분리한다. 편성 계층은 현재 압력, 최근 사건, 미해결 관계, 참여자 점유와 준비 가능성을 읽어 후보와 시점을 정해야 한다. 발생 조건의 재검사, 물건 소비, 작업 진행, 부상, 관계와 보상은 각 상태를 맡은 시스템이 처리해야 한다.

이 분리는 사건이 극적 필요를 이유로 물리 규칙을 건너뛰는 일을 막는다. 각 시스템은 사건의 전체 빈도까지 관리할 필요가 없고, 사건 편성은 물건 소비나 부상을 직접 결정하지 않는다. 후보 선정과 실행 결과를 각각 기록하므로 저장과 복원 뒤에도 같은 사건을 중복 실행하지 않는다.

현재 공통 사건 처리와 압력 기반 편성의 적용 범위는 [시스템 구현 권위 체크리스트](../system-implementation-checklist.md)가 판정한다.

## 조립식 콘텐츠 구조

반복되는 콘텐츠는 기존 모듈의 조합으로 만든다. 건물 하나를 추가할 때 배치, 전력, 입력 공간, 생산, 환경, 서비스와 저장을 모두 새로 만들지 않는다. 필요한 능력을 골라 기존 실행 규칙과 연결한다.

| 콘텐츠 | 조립하는 규칙 | 작성자가 결정하는 내용 |
|---|---|---|
| 건물 | 배치, 방, 기반망, 생산, 서비스와 저장 능력 | 크기, 분류, 연구 조건, 건설 조건, 제공 능력과 운영 요구 |
| 아이템 | 물리 속성과 음식·약품·장비 같은 용도 규칙 | 재고 분류, 용도, 소비 규칙과 고유 상태 여부 |
| 생산식 | 입력, 작업, 설비, 출력과 부산물 | 구체 재료, 작업량, 설비 요구와 결과 |
| 작업 | 발생 조건, 긴급도, 수행 자격과 실행 규칙 | 일이 생기는 조건, 담당자, 실행과 중단 방식 |
| 연구 | 선행 연구, 시설 요구와 해금 결과 | 기술 인과, 연구 작업, 새로 열리는 행동과 시설 |
| 사건 | 발생 조건, 참여자, 선택 비용, 결과와 경보 | 언제 누구에게 발생하고 무엇을 바꾸는가 |
| 시설 합성 | 합성 조합식, 실제 시설 재료와 연구 조건 | 무엇을 재료로 어떤 시설을 조립하는가 |
| 시설 진화 | 사용 이력, 변화 후보, 비용과 결과 | 어떤 사용 이력이 어떤 변화 후보와 비용을 만드는가 |
| 침입과 원정 | 적, 조우, 결정, 목표와 전장 수정자 정의 | 전술 역할, 준비 조건, 전장 규칙과 결과 유형 |

기존 의미만 조합하는 콘텐츠는 데이터 작성으로 끝나는 것이 이상적이다. 새로운 의미가 필요하면 재사용할 수 있는 규칙을 하나 추가하고 같은 작성 경로로 노출한다. 새 건물마다 중앙 코드에 전용 분기를 더하면 콘텐츠 수가 늘수록 수정 범위가 커지고, 같은 기능이 서로 다른 규칙으로 작동할 위험이 생긴다.

### 조립식 설계가 재미에 기여하는 방식

모듈화는 개발 효율과 플레이 규칙의 일관성을 함께 확보한다. 같은 능력이 여러 콘텐츠에서 같은 규칙으로 작동하면 플레이어는 이미 배운 지식을 재사용할 수 있다. 연료 소비를 이해한 플레이어는 새 발전기나 화덕을 보았을 때 어떤 물류 문제가 생길지 예상할 수 있다. 시설 기능과 환경 요구가 일관되면 새 병동이나 연구실도 기존 공간 지식으로 판단할 수 있다.

콘텐츠의 차이는 능력, 비용과 위험을 묶는 방식에서 나온다. 새 시설이 기존 모듈을 조합해도 입력 자원, 설치 위치, 필요한 인력, 환경 민감도와 출력 소비처가 다르면 운영상 다른 결정을 만든다.

## 새 콘텐츠를 추가하는 판단 순서

### 기존 모듈로 표현할 수 있는 경우

새 건물이 전력을 소비하고, 특정 방 환경을 요구하며, 물리 입력을 받아 생산하고, 출력 공간을 가진다면 기존 능력과 생산 경로를 조립한다. 새 아이템이 음식, 약품, 탄약이나 설치 부품의 기존 의미에 속한다면 해당 용도 규칙을 작성한다. 새 작업도 발생 조건, 긴급도, 수행 정책과 기존 실행 규칙의 조합으로 해결되는지 먼저 본다.

이때는 작성한 콘텐츠가 실제 실행 경로에 연결되는지 확인한다. 자산 파일이 존재하고 목록에 등록되어도 어떤 시스템도 읽지 않으면 플레이에 나타나지 않는다. 콘텐츠 데이터베이스의 실행 경로 항목은 이 연결을 정적으로 확인하는 보조 근거다.

### 새로운 시스템 의미가 필요한 경우

새 효과가 신체 기관을 영구 교체하거나, 새로운 인계 상태를 만들거나, 기존에 없던 장기 사건 진행을 요구한다면 데이터 한 줄로 숨기지 않는다. 다음 경계를 함께 설계한다.

- 불변 정의와 안정 ID
- 상태를 변경할 권위
- 변경 요청과 사전 검증
- 실제 실행 과정
- 취소, 파괴와 부분 실패
- 저장 범위와 버전
- 상태 조회와 플레이어 피드백
- 다른 시스템이 읽을 결과나 영수증
- 자동 감사와 결정론적 검증

새 의미를 타입화하면 이후 콘텐츠는 다시 그 모듈을 조립해 사용할 수 있다. 반대로 한 콘텐츠 전용의 숨은 상태로 넣으면 두 번째 콘텐츠부터 규칙이 갈라진다.

## 구조가 보호하려는 플레이 경험

이 아키텍처가 지키려는 것은 다음 세 가지다.

첫째, 결과에 대한 신뢰다. 생산된 물건, 치료된 부상, 세력과의 약속과 원정 결과가 저장 후에도 같은 사실로 남아야 한다.

둘째, 원인의 가독성이다. 실패가 어느 권위와 어느 단계에서 일어났는지 구분되어야 플레이어가 재료, 공간, 작업, 정책과 위험 중 무엇을 고칠지 알 수 있다.

셋째, 콘텐츠 규모의 통제다. 수백 개의 시설과 아이템을 다루면서도 같은 의미를 같은 방식으로 실행해야, 새로운 조합이 기존 세계 규칙 안에서 예측 가능하게 작동한다.

현재 구현 상태와 아직 공통 계약이 없는 영역은 [시스템 구현 권위 체크리스트](../system-implementation-checklist.md)에서만 판정한다. 저장과 복원의 자세한 구조는 [저장, 복원과 이어지는 세계](09-save-restore-determinism-and-validation.md), 코드 위치는 [근거 지도](appendix-source-map.md)를 따른다.
