## 3. 반드시 수정할 계약 경계

### F1. 캐릭터 복원 후보의 준비·스테이징·폐기 수명이 일관되지 않음 — P1

대상: [CharacterWorldSaveService.PrepareRestoreCandidate](../../Assets/Scripts/Services/Infrastructure/CharacterWorldSaveService.cs#L1111), [StageRestoreCandidate](../../Assets/Scripts/Services/Infrastructure/CharacterWorldSaveService.cs#L1293), [DiscardRestoreCandidate](../../Assets/Scripts/Services/Infrastructure/CharacterWorldSaveService.cs#L939), [CharacterWorldRestoreCandidate.Discard](../../Assets/Scripts/Services/Infrastructure/CharacterWorldSaveService.cs#L104).

**확인한 문제:** 동일 서비스가 `preparedCandidate`, `stagedCandidate`, `activePublication`, `restoreTransactionActive`와 외부 후보 조회 인덱스를 따로 관리한다. `DiscardRestoreCandidate()`는 staged 후보만 파괴하고 `preparedCandidate`를 비우지 않는다. 반대로 `PrepareRestoreCandidate()`의 진입 검사는 prepared 후보만 보고 staged 후보와 진행 중 publication을 검사하지 않는다.

소스에서 성립하는 호출 순서는 다음과 같다.

1. `BeginRestoreCandidate → Prepare(A) → DiscardRestoreCandidate → Prepare(B)`: A가 prepared 필드에 남아 마지막 호출이 `already prepared`로 거절된다. 호출자가 A 토큰을 따로 `Discard()`하면 정리할 수 있으므로, 두 폐기 경로의 조합에 성공 여부가 달려 있다.
2. `BeginRestoreCandidate → Prepare(A) → Stage(A) → Prepare(B)`: Stage가 prepared를 null로 만들기 때문에 서비스의 진입 검사를 통과한다. 다만 `RestoreWorldCandidateIndex.SetCharacterCandidate()`가 중복 후보를 거절하므로 A의 조회를 B로 덮지는 못한다. 문제는 payload 검증/배우 구성 등 불필요한 준비를 진행한 뒤 너무 늦게 거절한다는 점이다. staged/published 상태는 준비 진입에서 거부해야 한다.

실제 생산 경로는 [CharacterWorldSaveSection](../../Assets/Scripts/Services/Infrastructure/Save/WorldAndCharacterSaveSections.cs#L224)과 [DungeonSaveSectionRegistry.RestoreAll](../../Assets/Scripts/Services/Foundation/Save/DungeonSaveSections.cs#L621)이다. 정상 registry 경로는 stage 토큰과 participant를 순서대로 정리하므로 위 문제를 매 복원에서 일으킨다고 볼 수 없다. 문제는 공개 수명 API가 잘못된 상태 조합을 허용하고, participant 폐기만으로 준비 상태를 정리하지 못한다는 데 있다.

## 6. 952파일 순환의 해석과 처리 범위

952는 **가장 큰 강연결 그룹에 포함된 파일 수**다. 독립된 버그 952개나 필요한 신규 클래스 952개가 아니다. 파일에 계약과 구현이 함께 있거나 공통 façade가 여러 역할을 연결하면, 파일 그래프가 실제 상태 결합보다 크게 보일 수 있다.

전체 순환 그룹 20개 중 큰 그룹 하나와 작은 그룹 19개가 있다. 작은 그룹에는 원장 partial들, 포획 partial들, registry와 SO, 저장 transaction과 save section, 통계와 formatter 등이 들어간다. 이를 모두 같은 심각도로 취급하지 않는다.

현재 선택할 전략은 **문제가 발생한 업무 경계에서 필요한 참조 방향만 수정**하는 것이다. 독립 계산/검증이 live actor·UI·composition root를 끌어오는 경우에는 값 snapshot이나 기존 query port로 바꿀 수 있다. 타입 선언을 다른 파일로 옮기는 것만으로 실제 상태 수명이나 실패 계약이 좋아졌다고 보고하지 않는다. 인터페이스 파일 수를 늘리거나 SCC 0을 목표로 일괄 작업하지 않는다.

## 8. 권장 실행 단위와 완료 조건

1. **F1만 먼저 수정:** 현재 클래스의 상태 전이·폐기 계약을 고친다. 불필요한 파일 분할 없이 준비/취소/재시도와 공식 복원을 검증한다.
2. **F2 결과 의미 수정:** commit 이후 실패를 구분하고 UI까지 연결한다. completion/hook fault와 재시도의 상태 일치를 검증한다.
3. **기능 변경 수요에 맞춰 G1–G10 중 하나 선택:** 실제로 수정할 메서드와 그 상태만 분리한다. 기존 호출자·저장 ID·권위·취소 순서를 보존한다.
4. **여기서 멈춘다:** 관련 회귀가 없고 다음 기능 변경이 없다면 나머지 후보는 남겨 둔다. 전역 SCC 제거·모든 타입 2,000줄 미만·새 파일 수 같은 지표를 완료 조건으로 삼지 않는다.

향후 Unity 검증은 저장소의 비대화형 station/desktop 격리 실행만 사용한다. 이번 조사에서는 실행하지 않았으므로, 아래 구조 판단을 새로운 컴파일/PlayMode PASS로 읽으면 안 된다. 이전 batch29의 정상 복원 증거는 기존 동작의 참고이며 F1·F2의 예외 경로를 검증한 증거가 아니다.
