# 아키텍처 변경과 확장 인증

상태·저장·다중 도메인 계약을 바꿀 때 해당 절만 읽는다.
[루트 지침](../../AGENTS.md)의 위험 비례 검증과 사용자 승인 범위를 따른다.
이 문서를 읽었다는 이유로 전수 감사·카나리아·새 프레임워크를 기본 작업에 추가하지 않는다.

## 변경 전 확정할 계약

작은 국소 수정은 관련 소유자와 실패 경계를 확인하는 것으로 충분하다.
새 상태·저장 형식·다중 소유자 거래는 기존 계획에 다음을 짧게 확정한다.

| 경계 | 확정할 내용 |
|---|---|
| 정의·상태 | 불변 정의, 가변 상태의 유일한 쓰기 소유자 |
| 명령·조회 | 변경 진입점, 실제 UI/AI 호출자, 읽기 전용 투영 |
| 식별·저장 | 안정 ID, 저장 원본과 파생값, DTO 버전, 호환/마이그레이션 |
| 의존·실패 | 등록과 소비자, 수명, 실패 원자성, 취소/재시도 |
| 검증 | 변경된 실제 경로와 대표 실패·필요 저장 경계 |

새 계획 파일이나 동일 계약 표를 중복 생성하지 않는다.
기존 계약의 의미가 바뀌면 영향과 대안을 설명하고 현재 사용자 승인 범위 안에서 구현한다.

## 상태와 API 경계

- SO는 정의, Runtime은 상태, DTO는 저장 표현을 소유한다. 캐시와 UI는 권위를 복제하지 않는다.
- 상위 서비스는 게임 유스케이스를 조립하고 하위 계산·검증은 현재 씬·전역 싱글톤·UI 표현에 직접 의존하지 않게 한다.
- Unity 타입 자체를 제거하는 것이 목표는 아니다. GameObject 조립·표현·입력은 Factory/Presenter/Adapter 같은 경계에서 처리한다.
- 기존 시스템을 교체할 때 구형 쓰기 경로와 마이그레이션 경계를 명확히 해 이중 적용을 막는다.
- 함수 길이와 생성자 인자 수는 책임 검토의 단서다. 실제 별도 책임 없이 helper·partial·한 줄 전달 인터페이스를 늘리지 않는다.
- Unity 직렬화 타입·MonoScript GUID·저장 경계는 짧다는 이유로 합치지 않는다.

기존 상세 계약은 [상태 권위](../architecture/09-state-authority-ledger.md),
[도메인 간 거래](../architecture/10-cross-domain-transactions.md),
[확장 실무](../architecture/06-extension-playbook-and-assessment.md)를 참조한다.

## 확장 인증(명시적 요청 시)

사용자가 프레임워크 확장 인증이나 이에 해당하는 전체 검증 범위를 명시적으로 요청한 경우에만 이 절을 적용한다.
일반 P0 구현·작은 버그 수정·기존 데이터 추가에 synthetic canary와 모든 미래 조합 증명을 붙이지 않는다.

| 확장 유형 | 허용 범위 |
|---|---|
| ParameterContent | 기존 capability의 수치·참조·작성 데이터 변경 |
| ComposedContent | 등록된 capability/strategy를 선언적으로 조합 |
| NewCapabilityImplementation | 기존 인터페이스를 구현한 handler/policy와 descriptor 등록 |
| InvariantChange | 소유권·수명·저장 의미 등 불변식 변경; 별도 아키텍처 결정 |

인증 범위에서는 다음을 확인한다.

1. capability는 typed stable ID와 중복 거부를 사용하고 미등록 handler·codec을 명시적으로 거부한다.
2. 기존 capability 안의 콘텐츠는 공용 코어의 콘텐츠 ID 분기나 저장 DTO 재설계 없이 연결된다.
3. 가변 상태의 envelope·codec과 공용 조회/명령 경로가 새 조합에서도 권위를 유지한다.
4. 최소 하나의 synthetic canary를 기존 capability의 데이터/선언적 등록만으로 추가한다.
5. canary 전후 production core diff와 실제 정의→생산자→권위→소비자→저장/관찰 증거를 확인한다.
6. 입력 순서·locale·domain reload 등에 대한 결정론 검증은 합의한 인증 범위에서 수행한다.
7. [검증 도구](verification.md)가 검사하지 못하는 항목은 별도 검증 또는 미검증으로 남긴다.

현재 기능 동작과 미래 확장 인증은 다른 판정이다.
도구·정적 연결·fixture·실제 실행의 범위를 구분하고, 미등록 capability나 미연결 소비자를 기본값으로 숨기지 않는다.
