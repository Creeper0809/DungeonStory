## Production-entry atomicity correction — 2026-09-20

- The implementation re-review identified five P1 boundaries where the existing 57/57 evidence did not exercise the real mutation order: offense finalizer side effects before outcome commit, a stuck offense return-finalizing flag, V20 effects before outcome commit, three primitive-survival branches mutating before commit, and the breakdown world-drink branch mutating before commit.

- Exact survival implementation paths are `Assets/Scripts/Services/Survival/CharacterPrimitiveSurvivalRunner.cs`, `CharacterBreakdownActionRunner.cs`, and `Assets/Scripts/Models/Survival/Core/CharacterConsumablesRuntime.cs`.
- `TryConsumeFieldMeal` owns a two-stage physical meal commit and may return `DeliveryPending`; it is not a simple reversible need mutation. Primitive-survival must therefore reserve its migrated outcome before calling that command, then cancel only when the command makes no durable progress, rather than attempting to reconstruct the physical meal stack afterward.
- Existing world filth and water ports expose complete capture/restore state and next-sequence values. `CharacterBreakdownWorld` can safely expose a narrow snapshot/restore seam for the latrine and world-water branches without creating a second state authority.
- The offense return coordinator mutates actor lifecycle/experience before finalization and leaves `ReturnFinalizing` true if finalization throws. Any correction must snapshot/restore those actor owners and clear the in-flight flag in `finally`, not only wrap the finalizer call.
- Floor-rest establishes the intended primitive-survival ordering: durable migrated outcome first, gameplay effects second, observer event last. Latrine can use the same order directly; no world/actor rollback is needed when the commit precedes all mutations.
- Bucket-wash cannot commit the outcome before confirming the reserved item was consumed without risking a ledger row for a failed wash. It already has complete `IWorldItemStackRuntime.Capture/Restore`, so the narrow correction is reserve → capture physical/actor → consume/apply → commit → observer, with exact restore on definite rejection.
- The safe-water coordinator already contains the required reserve/capture/mutate/commit/restore contract for world sources. The duplicated breakdown path can adopt the same pattern through `CharacterBreakdownWorld` capture/restore methods, while retaining its special foul-water consequences after durable commit.
- `IFieldMealConsumptionCommand` currently exposes only find/consume. Its compatibility adapter owns the real `CharacterConsumablesRuntime`, whose public capture/restore-candidate API covers the meal workflow state but not the physical item owner. A field-meal rollback seam therefore needs both consumables state and `IWorldItemStackRuntime` state; neither may be silently omitted.
- `CharacterConsumablesRuntime` already records its own meal outcome inside the physical meal workflow. The primitive-survival completion is a second outcome; making it truly atomic with field-meal consumption requires either a joined ledger batch or a durable primitive-completion outbox tied to the completed consumables operation. - Offense reward application fans out to multiple external owners; `OffenseRewardRuntime` persistence covers only reward-runtime state, not every money/item/research/arrival sink. Restoring only that runtime after a rejected result would remain incomplete. - The offense result summary currently includes counts that are populated only after reward application. To place the ledger boundary first without lying, the committed summary should describe the authoritative battle/target result and treat reward/item/arrival/currency receipts as post-commit settlement details, rather than precondition the result commit on those fan-out effects.
- A post-commit offense finalization failure must remain retryable and idempotent. `ReturnFinalizing` needs `finally` cleanup, while reward/campaign/meta actions need either existing idempotent operation identities or an explicit expedition finalization progress owner before moving the commit earlier.
- `V20ContentResolutionService` already preflights item costs/grants, then commits money, reserved-item consumption, exact-source grants, and typed actor/domain effects before committing the batch of `V20ResolvedEventResult` rows. Its catch restores only the four campaign aggregates. The fix must expand a real effect-owner snapshot/restore transaction or join the result batch with the prepared effects; merely moving `CommitResolvedEventOutcomes` earlier would leave a durable false result when an effect later fails.
- The same ordering defect also exists in `CommitObservedLifeEvents` (effects and campaign publish precede outcome commit), so correction and regressions must cover both public request resolution and observed life-event paths.
- V20 typed effects span mood, trauma, progression, body health, social memory, population health, narrative history, money, and physical items.
