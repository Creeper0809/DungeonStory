# 사회 사건·손님 요청·서비스 사고 위키 대조

## 판정 범위

- 공개 위키 `0.0.1v`의 `events-and-choices` 가이드와 사건 엔티티를 현재 작성 자산, 일일 스케줄러, 선택 실행, 경보 UI, 저장 검증 코드에 대조했다.
- 현재 작성 모집단은 생애 사건 32개, 손님 요청 14개, 서비스 사고 8개로 총 54개다. 공개 사건 엔티티도 같은 세 계열이 각각 32/14/8개여서 **페이지 자체의 누락은 없다**.
- 정적 소스 감사이며 Unity Play Mode에서 실제 사건을 발생시키지는 않았다. 정의·호출·상태·UI·저장 코드를 분리해 판정했다.

## 작성 자산과 공개 엔티티

| 계열 | 작성 수 | 공개 수 | 작성된 선택/효과 | 공개 노출 | 판정 |
| --- | ---: | ---: | --- | --- | --- |
| 생애 사건 | 32 | 32 | 자동 12개는 효과 12행, 일반 20개는 선택 40개·효과 40행 | 모든 페이지에 분류 1개, 효과 관계 합계 49행 | 기한·쿨다운·빈도·자동 여부·선택별 요구/결과 수치 누락 |
| 손님 요청 | 14 | 14 | 요구 시설 14행, 요구 물품 13행, 성공 효과 28행, 실패 효과 14행 | 성공/실패 효과 개수 28 facts, 물품 요구 관계 13행 | 기한·시설·소모 여부·효과의 종류/값 누락 |
| 서비스 사고 | 8 | 8 | 사고별 대응 3개, 총 24개 효과 | facts 0, 효과 관계 합계 18행 | 사고 종류·대응 제목/결과와 6개 효과 관계 누락 |

생애 사건 분류는 유년기/도제/가족·동반자/경력 각 6개, 은퇴·노년/죽음·유산 각 4개다. 모든 32개는 `OncePerCharacter`다. 자동 12개는 기한 1일·정의 쿨다운 45일, 일반 20개는 기한 3일·정의 쿨다운 90일이다. 현재 작성 생애 사건에는 `emergency=true`가 없다.

손님 요청은 일곱 종류가 각각 2개다. 기한 분포는 2일 1개, 3일 2개, 4일 3개, 5일 4개, 6일 2개, 7일 1개, 8일 1개다. 14개 모두 가동 시설 하나를 요구하고, `monster-circus`를 제외한 13개는 물품도 요구한다. 서비스 사고는 여덟 종류가 하나씩 있으며, 현재 작성본은 모두 트리거/선택 요구 조건이 비어 있고 정확히 세 대응을 가진다.

## 실제 일일 발생 규칙

`V20CampaignApplicationAdapter`는 게임 날짜가 시작될 때 살아 있는 주민, 월드 지표, 시설·재고·세력 상태를 스냅샷으로 만들어 `EvaluateDaily`를 한 번 호출한다. 같은 절대 날짜는 다시 평가하지 않는다.

사회 사건 스케줄러의 실제 상한은 다음과 같다.

- 30일까지 일반 사건 동시 1개, 31일부터 일반 사건 동시 2개다.
- 서비스 사고와 `emergency=true` 생애 사건은 별도 비상 슬롯 하나를 사용한다. 현재 작성 비상 생애 사건은 0개라 비상 후보는 서비스 사고 8개다.
- 따라서 31일 이후에는 일반 2개와 비상 1개, 총 3개가 동시에 존재할 수 있다.
- 같은 정의는 생애 사건의 작성 쿨다운 45/90일, 손님 요청·서비스 사고는 30일 동안 다시 나오지 않는다.
- 같은 분류는 최소 3일 동안 다시 나오지 않는다.
- 선택하지 않은 사건은 `deadlineAbsoluteDay < currentDay`일 때 만료된다. 즉 표시된 마감일 당일까지 선택할 수 있다.
- 자동 생애 사건은 주민 한 명당 하루 하나만 배정되고 하루 최대 6개다.
- 후보 순서는 `runSeed + absoluteDay + definitionId (+ characterId)`의 stable hash와 작성 content weight로 결정된다.
- 활성 사건, 최근 해결 256개, once/세대/주민 빈도 키, 정의·분류 쿨다운, 작업 지연과 마지막 평가일은 저장 검증 대상이다.

공개 가이드의 “평상시 2~5일마다 1회, 위기 1~2일마다 1회”는 이 스케줄러의 강제 간격이 아니다. 실제로는 동시 슬롯, 정의/분류 쿨다운과 매일 후보 평가의 조합이다. 다른 분류 사건을 당일 해결하면 다음 날 새 사건이 시작될 수 있다.

## 선택 실행과 물리 자원

선택 버튼은 현재 사건 instance와 choice ID를 담은 action ID를 `V21ContentAlertChoiceActionDispatcher`로 전달한다. 실행 서비스는 다음 순서로 처리한다.

1. 활성 사건·선택·월드 요구 조건과 실제 가동 시설/대상 주민을 다시 검사한다.
2. 후보 캠페인 상태에서 사건 결과를 먼저 계산한다.
3. 비용 금화, 물품 소비 stack, 물리 보상의 배치/드롭 지점을 preflight한다.
4. 물품은 exact stack ID 순으로 예약하고, 금화·물품 소비·보상 publication을 커밋한다.
5. 주민·관계·세력·위협·질병·작업 지연 등 typed 효과를 적용한 뒤 후보 캠페인 상태를 게시한다.

이 경로에는 사건 전용 운반 목적지나 작업 주문이 없다. 요구 물품은 현재 월드의 사용 가능한 stack을 직접 예약한 뒤 제자리에서 원자 소비한다. 따라서 공개 가이드의 “선택 뒤 주민 이동·물건 운반 작업이 이어지고 경로를 확인한다”는 설명은 현재 사회 사건 54개 처리와 일치하지 않는다.

물리 보상은 drop zone을 먼저 확인하고 exact source publication transaction으로 준비한 뒤 지급한다. 보상 준비가 실패하면 비용 예약을 해제한다. 금화/물품 커밋 실패 때는 금화와 준비된 보상을 되돌린다. 물품이 이미 소비된 뒤 보상 publication이 실패하면 일반 실패 반환이 아니라 예외로 중단한다. 이 구조를 “모든 중간 실패가 완전히 롤백된다”는 문장과 동일한 일반 계약으로 과장하면 안 된다.

## 경보 UI와 가이드 차이

현재 사회 사건 경보는 모든 사건을 `High` 중요도로 게시한다. 본문에는 설명과 절대 마감일만 표시하고, 선택 버튼에는 선택 제목과 outcome text만 넣는다.

현재 표시하지 않는 것:

- 대상 주민·세력·시설·구역
- 발생 원인과 트리거 조건
- 선택별 물품·시설·연구·주민·세력·월드 조건
- 물품의 예약/운반 상태
- 위험도 또는 예상 비용·효과 수치
- 선택 뒤 실제 작업/경로 상태

공통 경보 중요도 enum은 `Low/Medium/High`뿐이며 `Critical` 등급이 없다. 경보 기록은 source ID가 같은 항목만 병합할 뿐 5개/2개 상한이나 중요도별 삭제 정책이 없다. 자동 생애 사건은 하루 최대 6개까지 바로 해결되어 개별 `V20ContentEffectsResolvedEvent`가 발행되지만 이를 하루 요약 경보로 만드는 subscriber는 현재 소스에서 찾지 못했다.

## 정상 연결과 보류

- 사건 54개의 작성 자산과 공개 엔티티 수는 정확히 일치한다.
- 서비스 사고는 작성본 8개 모두 기계적으로 다른 대응 세 개를 가진다.
- 요구 시설은 `mustBeOperational`일 때 실제 가동 여부를 확인한다.
- `ContentRequirementEvaluator`는 주민 요구가 작성되면 생애 단계, 체력, 필요/제외 특성을 실제 주민에 대조한다. 다만 현재 세 계열 54개에는 주민 요구 블록이 하나도 없어 이 기능을 현재 콘텐츠 누락으로 세지 않는다.
- 생애 사건/서비스 사고 선택 요구도 현재 모두 비어 있다. 스키마 지원을 현재 플레이 선택지의 다양성으로 과장하지 않는다.
- 알림 상한과 자동 사건 요약은 Unity 재현 없이 정적 연결 부재로 판정했으므로, 런타임 외부 플러그인이나 미추적 subscriber가 있다면 재검증해야 한다.
