## Minimum WIM-023 fix surface

Keep the existing five installation procedures and their producer/outbox route. Retain the nine verified treatment procedures and do not alter their WU/BOM/risk/health/infection values. The smallest WIM-023 state work is the six state-required entries above, only after their missing per-procedure target/part/policy choices are supplied; the nine ambiguous entries stay unchanged pending a meaning decision. This is a bounded classification and state-connection change, not a new medical framework or a WIM-014 cold-storage change.

One concrete replacement-ownership gap remains in current source: `CharacterBodyHealthRuntime.TryReplaceNodePart` returns the prior `AnatomyNodeHealthState`, including its previous `installedPartId`, but `InstallSurgicalPartEffectHandler` discards it (`out _`). `SurgicalPartInstallationOutbox` marks the incoming part installed and clears its physical stack; no source path clears, returns, or otherwise records the prior installed part. Replacing a node that already contains a surgical part can therefore leave that previous `SurgicalPartInstance.installed=true` while the body node now points to the new ID.

P02's “already installed part rejection” and its replacement-ownership requirement are consistent only with a procedure policy split: an **install-only** species procedure rejects a target whose `installedPartId` is nonempty, whereas a deliberately **replacement** procedure may replace it and must give the old part a transactional disposition. A **tuning/reinforcement** procedure has a third policy: it operates on the existing state without consuming/replacing an unrelated new part. Current generic installation instead replaces every present character node, so it cannot stand in for all three policies.

For an approved replacement only, the narrow repair is an explicit disposition step when the prior node has a nonempty installed part ID: update/rehome/decommission that exact previous part under one transactional receipt contract, then write the new node reference. The required focused proof is: install A, reject a second install-only attempt; then replace A with B, verify one live body reference, exact old-part disposition, no duplicate physical stack, and save/restore/replay identity. This is separate from the existing incoming-part transfer receipt.

## Approved replacement-recovery transaction supplement

### Current execution order and the uncovered windows

The live character path currently executes in this exact order:

1. `InstallSurgicalPartEffectHandler.ApplyTyped` resolves the selected part and snapshots the current anatomy node.
2. `SurgicalPartRuntime.TryConsumeForInstallation` writes the incoming installation intent, commits a physical `Transfer`, then `SurgicalPartInstallationOutbox.TryFinalizePending` marks the incoming part installed, clears its world stack, and acknowledges the receipt.
3. Only after that terminal incoming acknowledgement does the handler call `CharacterBodyHealthRuntime.TryReplaceNodePart`. The method clones and returns the old node, writes the new part ID/kind/efficiency into the body, and the handler discards the returned clone.
4. No call changes the old `SurgicalPartInstance`, creates an old-part output, or records an old-output receipt. `SurgeryRestoreCoordinator.ReconcilePartInstallationDispositions` only finalizes the incoming transfer; it has no old-part/body-replacement join.

Consequently, the incoming part and its physical stack can reach terminal transfer state before the body references it, while the final steady state can leave both the old and new `SurgicalPartInstance` records marked installed for one subject. Save validation checks installation provenance and subject existence, but does not join a character anatomy node to exactly one installed part owner. A naked `SpawnUniqueItemAt` after the body mutation would add a second crash window: retry could duplicate the output, while failure before spawn would lose it.

Two identity fields are also missing for the approved recovery result. `SurgicalPartInstance.partInstanceId` and `quality` survive installation, but the physical stack's `ItemInstanceId` is not copied into the part before `worldStackId` is cleared. Part durability exists only as the installed anatomy node's health/condition; there is no detached-part durability field. Exact recovery therefore requires preserving the same surgical part ID, the same physical item-instance ID, the same quality, and a lossless persisted durability value captured from the returned pre-replacement node. Infection, rejection/mutation burden, `moduleBonus`, new species effects, new part definitions, and tuning values are not implied by that approved durability contract.

### Required structural contract

| Boundary | Required invariant |
|---|---|
| Admission | A replacement operation has one deterministic identity derived from order, subject, target node, old part, and incoming part. The body must still reference the expected old part; exactly one old part must be installed for that subject; and the incoming part must still be reserved by the same order. Any different old/new/body tuple is a conflict, not a replay. |
| Output-space wait | Before result finalization, incoming consumption, or body mutation, reserve real physical output capacity for one exact old-part output at the operating facility. Capacity rejection leaves the same order in a retriable output-wait state: no RNG reroll, extra WU/material charge, incoming transfer, body change, or old-part publication. Current surgery facilities expose no common physical recovery-output capacity owner. `PhysicalItemExactSourcePublicationService` creates a self-sized private Source destination, so using it alone would not prove that the facility had output space. The bounded existing-destination join and evidence-based initial authoring recommendation are specified below. |
| Prepared output | After capacity admission, prepare an exact unique Source output before changing body ownership, following the existing equipment-module return pattern. The prepared subject and component must bind the old surgical part ID, preserved physical item-instance ID, kind/node, quality, and durability to one prospective stack and one deterministic batch commit. A transient prepared publication must keep the existing save-capture guard closed until rollback or commit-forward completes. |
| Incoming receipt | Split the existing installation finalizer so the physical incoming `Transfer` may remain pending while replacement commits. It must not mark/acknowledge the incoming part terminally installed before the body compare-and-swap and old-output ownership are ready. The pending receipt remains the sole custody proof for the removed incoming stack. |
| Body/part commit | Replace the body by compare-and-swap on `expectedOldPartId`. On first execution, capture the old node durability, point the node to the incoming part, mark the incoming part installed, and detach the old part onto the prepared output stack. On replay, an already matching new node is accepted only when incoming/old part records and receipts match exactly; a node pointing anywhere else fails loudly. |
| Output receipt and acknowledgement | Commit/release exactly the prepared old stack, then acknowledge both old-output and incoming-transfer receipts and retire the replacement intent. The old part becomes loose/haulable with one `worldStackId`; it is no longer installed and has no installed subject. Receipt replay validates the same batch/stack/item-instance/component vector and never allocates or spawns a second stack. |
| Failure and restore | Before the domain compare-and-swap, failure rolls back the prepared old output and leaves the old body/part and incoming reservation unchanged. After compare-and-swap, recovery is commit-forward only. Save capture is legal only in the pre-operation or fully terminal state unless a persisted replacement phase owns every intermediate receipt. Restore must either validate the untouched pre-state or validate/finalize the exact new-body + incoming-installed + old-loose-stack terminal join; mixed body/part/output tuples are rejected. |

`SurgeryRuntime.ApplyWork` currently sets `resultRolled=true` before invoking effects and treats an effect failure as a paused/failed outcome, so a capacity failure cannot simply be returned from the present handler. The output-space gate must occur before that roll, or the order must persist a non-rerollable successful outcome plus effect progress. The smaller contract is pre-roll capacity admission followed by one synchronous, save-guarded replacement transaction.

### Capacity join resolution (recommended)

Reuse the existing per-order `SurgeryMaterialDestinationAuthority` destination at the selected primary operating facility as the one shared physical surgery buffer; do not add a second recovery registry or route the removed part directly to storage. Its claim is already a live-facility, exact-gram destination at `facility.centerPos`, and the generic planned-output admission path does not restrict the owner to production. A recovery publication can therefore target the same destination/profile and use the normal `IFacilityBufferMassAdmissionService`: admission counts non-carried buffered mass, committed carried mass, and all outstanding reservations for that destination. This makes the selected incoming part and any unfinished input delivery compete with the old-part output reservation instead of granting the recovery a private capacity. On terminal closure, the existing surgery custody drain releases deposited stacks at the operating-facility position; the recovered part then becomes a normal loose, haulable world stack rather than being teleported to another warehouse.

The two nearby registered profiles are not substitutes:

- `SurgicalPartStorageInputOwnerAuthority` publishes the `BuildingOrganStorageAbility` facility's own destination at the organ-storage position, backed by `BuildingStorageAbility.maxStoredMassGrams` (`M08` authors `12500`). It is a persistent storage-input owner, not the selected operating facility. Publishing the removed part there would bypass the required operating-facility output wait and perform the forbidden immediate remote-storage disposition.
- `SurgicalPartProductionOutputHandler` uses the production-output destination and `BuildingProductionBufferAbility` of `M06`. `M06` is a prosthetic assembly support (`IsPrimaryOperatingFacility=false`), and the production capacity projector requires a production workstation/output contract. Its profile is valid precedent for exact planned-output admission but cannot own an installation result performed at `M03`, `M09`, or `M12`.

The current surgery profile is nevertheless insufficient as authored: `SurgeryMaterialDestinationRuntime.TryCaptureCapacity` sizes it exactly to that order's required materials plus selected incoming part. The primary operating assets have only count-based `BuildingInternalStockAbility.capacity=12`; none authors a general output or mass capacity. The minimum bounded authoring addition is one surgery-specific building ability, for example `BuildingSurgerySharedBufferAbility.maxMassGrams`, read by `SurgeryMaterialDestinationRuntime` as the **fixed total** capacity of the existing material destination. The runtime must verify that the deterministic input projection fits that fixed value, persist/fingerprint the authored value, and reserve the removed output against the same profile. It must not add the input projection to the authored capacity, because that would recreate a self-sized destination and prevent genuine input/output contention.

Use `12500g` only as the initial authoring candidate on every primary operating facility that can host a replacement. `M08` organ storage already authors that value for surgical-part mass custody, so it is a nearby scale reference, not evidence that an operating facility physically has the same space. Current unique surgical parts are `800g` natural organs or `1800g` prosthetics. The largest current replacement admission envelope is the prosthetic-installation route: authored inputs and supports total `3220g`, the incoming prosthetic is `1800g`, an unwilling unrestrained subject can add `2500g` restraints, and the largest removed part adds `1800g`, for `9320g` total. The `12500g` candidate would admit every current replacement while leaving `3180g` observable headroom; filling that headroom through the same destination must produce the approved retriable space wait. The value still requires operating-space authoring approval, and future heavier parts or material changes must pass the same mass audit rather than silently increasing capacity.

The fixed profile also requires a facility-owner cardinality invariant. Current `SurgeryRuntime.TrySchedule` rejects only another active order for the same subject. It may select a facility already referenced by another active order, then immediately assigns a new order-derived `materialDestinationId` and calls `TryClaim`. `TryGetWorkFor` merely chooses the highest-priority clinical order at that facility; it does not prevent multiple waiting/active owners. Restore likewise rebuilds one profile per active order. Because `FacilityBufferMassAdmissionService` accounts occupancy and reservations by `DestinationId`, not by `OwnerFacilityId`, two orders at one facility would each receive the full fixed capacity and duplicate the physical space.

A simple no-registry candidate is to reject a second nonterminal order for an already-owned primary facility. That would match the authored facility-use capacity of one, but it removes the existing ability to reserve multiple surgeries against one facility and is not approved. The existing admission service has no cross-destination aggregate-capacity group to reuse, so retaining multiple simultaneous physical destinations would require a broader shared-capacity authority decision.

### Queue-preserving physical-owner alternative (feasible)

The logical reservation queue can be retained without duplicating physical capacity by allowing multiple active orders for one facility but allowing only one of them to own a material claim/profile, input delivery, or patient admission. No new persisted field or order state is strictly required. The existing material-authority tuple is unambiguous if validation makes it explicit:

- A queued order remains `PatientWaiting`, keeps its canonical order-derived `materialDestinationId` and selected-part `reservedOrderId`, but has `materialBufferCapacityGrams=0`, `materialMassAuthorityRevision=0`, an empty `materialCapacityFingerprint`, and no claim/profile. It must also have no material request/consumption or sink state, no process-fluid consumption, no patient admission/transport, no doctor owner, and no terminal-drain state.
- A physical execution owner is the same order after `SurgeryMaterialDestinationRuntime.TryClaim` has atomically populated the positive capacity/revision/fingerprint tuple and matching claim/profile. Only this tuple may call `RequestMissingMaterials`, `PrepareAdmission`, or enter clinical work.

Current code does not yet accept that split: `TrySchedule` always reserves the selected part, claims a destination, requests materials, and prepares admission before adding the order; `Tick` drives every active order; `SurgerySaveValidation` requires positive material authority for every active order; and restore rebuilds profiles for every active order. The queue alternative therefore changes execution timing, not scheduling entitlement: a second order is still created and its exact part remains reserved, but its materials and patient stay at their current owners until it wins the facility.

Activation can be deterministic within `SurgeryRuntime`: for each facility with no physical execution owner, choose one valid queued order by the existing urgency, `createdAt`, then `orderId` ordering; revalidate the subject, facility, and exact selected-part reservation; then claim the destination and start the existing logistics/admission calls. `TerminalDraining` retains physical ownership until custody drain and authority revoke complete, so the next queued order cannot activate in the old output's crash window. A queued selected part that expired or lost its exact `reservedOrderId` fails/cancels before claim rather than creating material custody for an invalid input.

Cancellation and destruction require a two-path close. An activated order keeps the existing terminal custody drain. A claimless queued order has no physical destination or patient to drain, so cancellation releases only its exact selected-part reservation and records the terminal order state with `materialTerminalDrainPhase=None`; the current validator already permits a terminal order with an empty drain tuple. If the authored facility is destroyed, all claimless waiters close through that path, while the one activated owner completes the existing destination drain using its persisted owner position. Temporary facility unavailability leaves queued reservations waiting and creates no claim.

Restore must preserve the split rather than promote every waiter. `SurgerySaveValidation` should admit only the exact empty queued tuple above and cross-check its selected part points back through `reservedOrderId`; partial authority fields or any queued logistics/transport state remain invalid. `BuildActiveMaterialFacilityPositions` and `SurgeryMaterialDestinationRuntime.TryReplace` must rebuild only orders with the complete positive authority tuple and reject more than one such owner per `facilityId`; queued orders remain claimless after staging. The first normal tick may then activate one deterministically. This reuses the current order list, part reservation, material destination authority, and save payload fields without a separate registry or facility-capacity group.
